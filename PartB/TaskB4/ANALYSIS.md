# B4 production decision
For 12 campuses and approximately 100 times the current pass volume, a shared relational database is the most suitable primary store. It supports concurrent counters, transactions, constraints, indexed searches, central reporting and controlled access. Text files are useful for exports, interchange and backups but do not naturally provide multi-user transactional updates. Java serialization is useful for Java object snapshots but is not an appropriate shared multi-campus operational database.

The migration program reads each legacy line, validates field count and numeric fields, collects valid rows, records rejected rows with line numbers and loads valid rows through the B3 batch loader in one transaction. DatabaseMetaData reports database product/version, JDBC driver/version and tables.

Alternative: one serialized file per campus avoids a single shared file but requires a separate search across 12 stores. If each campus has n passes, searching all campuses by scanning requires O(12n) time in the balanced case and total storage is O(12n). Synchronisation, file locking, duplicate resolution, backup and merging become campus-specific concerns. Concurrent counters writing the same campus file need locks or a single-writer service; a shared database provides transaction isolation and coordinated updates across campuses. Separate campus files may reduce network dependency but make central search and consistency more difficult.
